## Architectural Decisions

**Contract sharing.** `shared/schema.graphql` is the single source of truth for the API; the backend loads it directly to build the Apollo schema. `shared/src/types.ts` hand-mirrors that SDL as plain TS interfaces imported by both frontend and backend. I deliberately skipped GraphQL Codegen — it guarantees zero drift, but the pipeline setup (config, watch mode, generated-client wiring) costs more time than it saves at this scope for a 3-hour box. Hand-written shared types was the pragmatic call here; codegen would be the first thing I'd add back if this grew past a take-home.

**Book formats.** Modeled as a native Postgres enum array (`formats Format[]`) directly on `Book`, *not* a separate `BookFormat` model. A format has no independent data here — no per-format price or stock, just "this book is available as X" — so a join table would be pure ceremony. The format actually purchased is recorded as a plain enum value on `OrderItem` at checkout time.

**Explicit join tables (`BookAuthor`, `BookGenre`) instead of implicit Prisma many-to-many.** Driven directly by the assignment's stated target scale (10,000 books × 10,000 authors). Implicit m2m relations only support row-at-a-time `connect`, which doesn't bulk-insert — at that scale that's ~15–20k individual relation writes, likely tens of seconds to minutes. Explicit join models let the seed script use `createMany` everywhere instead, turning that into a few seconds. The public API surface (`Book.authors`, `Book.genres` as plain lists) is unaffected — this is purely an internal storage/seeding decision.

**Pagination — offset-based.** `page`/`pageSize` with Prisma `skip`/`take`, plus a returned `totalCount`/`totalPages`. At ~10k books this is plenty fast on an indexed table, and offset pagination is what naturally supports page-number UI controls (jump to page N), which the assignment calls for. Cursor pagination is the better answer for infinite scroll or very high-churn data, and neither applies here.

**Search — plain `ILIKE` fragment match** (Prisma `contains`, case-insensitive) on `Book.title` OR `Author.name`, combined with the same pagination via an `OR` filter. No `pg_trgm`/GIN index: at 10k rows a sequential-ish scan is still fast, and indexing wasn't picked as one of the two bonus features — noted here as the obvious next step if the catalog grew meaningfully larger.

**Rating aggregation** is computed per-request — a single batched `groupBy` over `Review` for however many book ids are on the current page (or in a user's order history), merged into the book DTOs — rather than denormalized onto `Book`. Avoids both an N+1 query pattern and premature caching complexity for a dataset this size.

**Genre report assumption.** Since a purchased book can belong to more than one genre, a purchased book's quantity counts toward *every* genre it belongs to. Implemented as a raw SQL join (`OrderItem → BookGenre → Genre`, `SUM(quantity)` grouped by genre) since Prisma's `groupBy` can't traverse a many-to-many relation on its own.

**No `Cart`/`CartItem` server model.** The cart is client-only React state, persisted to `localStorage` and namespaced by the currently selected user id, until checkout — at which point a single mutation atomically creates the `Order` + `OrderItem`s. There's no auth/session to hang a server-side cart lifecycle off of, so modeling one would be pure overhead.

**Checkout transaction safety.** `checkout` runs inside a single `prisma.$transaction`: it creates the `Order` and all of its `OrderItem`s together, and snapshots each book's *current* price into `unitPrice` at the moment of purchase (so a later price change never rewrites history). This is one of the two additional features (see below).

**User selection.** No auth — the "current user" is a plain dropdown, per spec. Given ~1,000 users, a plain `<select>` would be unusable, so this became my second additional feature: a debounced, backend-filtered, paginated combobox (search-as-you-type against `users(search, limit, offset)`, with a "Load more" control) instead of shipping the full list to the browser.

## AI Output I Intentionally Changed

The clearest example: **`UserCombobox`'s "Load more" button had a real, subtle bug that I only caught by actually clicking around in the running app.**

What the AI (me, in an earlier turn of this same session) originally generated: a `hasMore` boolean tracked in `useState`, synchronized inside a `useEffect` keyed only on the debounced search term:

```tsx
useEffect(() => {
  setExtraUsers([]);
  setHasMore(firstPageHasMore); // firstPageHasMore derived from `data`
}, [debouncedSearch]);
```

This looks reasonable at a glance, but it's wrong: on mount, that effect fires *before* the initial GraphQL query has resolved, so `firstPageHasMore` is computed from an empty pre-fetch `data` and freezes `hasMore` at `false`. Because the effect's only dependency is `debouncedSearch`, it never fires again once real data arrives — so the "Load more" button silently never appeared, even though there were clearly more than 20 users to page through.

I only found this because I asked the user to click through the running app, and they came back with "I don't see the button in the dropdown?" — a good example of an AI-generated implementation that type-checks, passes a shallow read-through, and is still functionally broken. What I changed: stopped syncing derived state through an effect at all. `hasMore` is now computed fresh on every render directly from the query's `data` for the first page, with a separate `lastPageHasMore` state that *only* the "Load more" handler itself touches for subsequent pages. No effect-timing race is possible once the value is derived rather than synchronized.

A second, smaller example of the same underlying lesson (an AI-generated `Select` that "looks right" but silently displays the wrong thing): the genre filter and the per-book format picker both used shadcn's `<SelectValue />` with no way to resolve a label, so the *closed* trigger displayed the raw `value` (a genre's database ID, or the literal enum string `HARDCOVER`) while the *open* list correctly showed friendly names — because the friendly labels only existed on `<SelectItem>` children, never wired into the closed-state display. This was flagged by the person I was working with, not caught by me proactively, in two separate but structurally identical bug reports ("closed it shows the genre ID" / "genres have a similar issue where it shows uppercase"). Fixed both by giving `<SelectValue>` a formatter function that looks up the real label instead of falling back to the raw value.

I've also included, as an aside: Apollo Client v4 deprecated passing explicit `<TData, TVariables>` generics directly to `useQuery`/`useMutation` in favor of typing the `gql` document itself as `TypedDocumentNode<Data, Variables>`. I'd written the original query hooks the old (now-deprecated) way; the person I was working with noticed the deprecation warning and asked me to investigate, and I re-typed every operation document accordingly.

## Two Additional Features I Chose

Decided up front, before any implementation code, alongside the plan/schema (see `CHATLOG.md`):

1. **Checkout transaction safety (data integrity).** `checkout` wraps the `Order` + `OrderItem` creation in a single Prisma `$transaction`, with `unitPrice` snapshotted from the book's live price at that moment. Valuable specifically *because* the assignment explicitly calls out "ensure the current price is memoized... so if the price changes in the future, we have a record of what was actually paid" — this makes that requirement airtight rather than "usually true," and it was cheap to do right from the start (a few extra lines) versus expensive to retrofit later.

2. **Searchable, paginated user dropdown (UX).** The assignment explicitly flags that ~1,000 users needs "basic usability implications" considered for the dropdown. A plain `<select>` with 1,000 `<option>`s is a real, common UX failure mode. This became a debounced, backend-filtered combobox (`users(search, limit, offset)`) with a "Load more" affordance rather than shipping the whole user table to the browser — directly addressing scalability (small payloads regardless of user count) and UX (the person actually using this app can type "Ava" instead of scrolling a 1,000-item list) at once.

*(A number of smaller UX refinements — URL query-param syncing for shareable/bookmarkable Browse filters, a stale-while-refetching pattern to avoid flashing the book grid, an editable-rating flow — were added later in the session at the user's request. Those are documented in `CHATLOG.md` and in the "Assumptions & Tradeoffs" section below where they deviate from the literal spec, but they're incremental polish, not the two additional features being submitted for this specific requirement.)*

## Assumptions & Tradeoffs Due to Timebox

- **Reviews are editable, not immutable — a deliberate, explicit deviation from the spec.** The assignment states reviews should be "format-agnostic and immutable (no editing or deleting)." Partway through the session, the person I was working with asked: "allow another selection to edit the rating if one already exists instead of blocking it (updating the average)" instead of rejecting a second submission outright. I implemented this as a Prisma `upsert` on the `(bookId, userId)` unique constraint. The "one review per user per book" *data-integrity* requirement is still fully enforced (there is still exactly one `Review` row per user/book pair) — only the "immutable" sub-requirement was relaxed, at explicit user direction, in favor of better UX (a misclicked star rating shouldn't be permanent). Flagging this clearly since a grader comparing strictly against the written spec would otherwise read it as a missed requirement rather than an intentional, directed change.
- **No GraphQL Codegen** (see Architectural Decisions above) — hand-written shared types instead, a documented time/drift tradeoff.
- **No trigram/GIN index for search** — plain `ILIKE` is fast enough at ~10k rows; would revisit if the catalog grew an order of magnitude larger.
- **No dedicated book detail page** — the assignment explicitly allows this; all relevant fields plus review/cart controls live on the browse-view card.
- **No payment integration, no email, no auth/session** — all explicitly out of scope per the assignment.
- **Order history pagination and the Report page's cross-user order feed, and URL query-param syncing for Browse/Orders,** were built later in the session as incremental UX polish once the core flows were solid, rather than being part of the original "two additional features." Included because they were cheap once the underlying query patterns already existed, not because they were required.

## Reflection: AI Usage

**What did AI significantly accelerate?** Almost everything mechanical and pattern-following: scaffolding three workspaces with consistent tooling, writing the Prisma schema and a batched, `createMany`-based seed script that hits real assignment-scale volumes in seconds, wiring up Apollo Server/Client end to end, and building out a full React UI (contexts, hooks, components, three routed pages) from a written plan. None of that is *hard*, but it's the kind of work where an AI agent turns hours into minutes as long as someone is actually directing it — deciding the schema shape, the pagination strategy, which two bonus features to build, and when to stop polishing — rather than just accepting whatever comes out first.

**Where did AI make things worse, or at least not better?** Twice, tooling-level bugs that had nothing to do with the actual application logic ate real time: a `shadcn add` CLI run that silently wrote generated components into a literal `frontend/@/...` directory instead of resolving the path alias into `src/` (happened twice — once during initial scaffolding, once when I ran the CLI again later), and a Vitest config that was double-counting tests because stray `dist/` build output wasn't actually excluded despite looking like it should be by Vitest's documented defaults. Neither was an "AI reasoning" failure exactly, but both are the kind of quietly-wrong tooling behavior an agent will confidently plow through without a human noticing something's off — I only caught them by inspecting the actual file tree and test counts rather than trusting a green checkmark. The `UserCombobox` `hasMore` bug (above) is the sharper example: code that reads as correct, passes a type-check, and is subtly wrong in a way that only running the app surfaces.

**What risks does AI introduce into engineering workflows?** The main one, concretely observed in this session: an AI agent will produce plausible-looking code with real logic bugs (stale-effect timing, in this case) that neither a type-checker nor a superficial read-through catches — it takes either genuinely exercising the feature or a careful trace of *why* an effect's dependency array is correct, not just that one exists. The second risk is scope/spec drift: it's easy for an agent to "helpfully" implement a requirement slightly differently than written (as I did with editable reviews) without it being flagged loudly enough — that only stays safe if every such deviation is explicitly surfaced and justified, as I've tried to do above, rather than silently smoothed over. The mitigations that actually worked here were boring but effective: real integration verification against a live backend instead of trusting mocks alone, explicit written justification for every deviation from spec, and treating "the AI said it's done" as a claim to verify, not a fact to report upward.
